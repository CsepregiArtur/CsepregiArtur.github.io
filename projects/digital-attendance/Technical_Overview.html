Digital Attendance at the Workplace

Attendance Control · v1.0.0

A local, offline kiosk time-tracking system. Employees scan a Code 128 badge at the door; the application validates every scan against shift rules, records clock-in / clock-out sessions in a local SQLite database, and hands administrators a full management shell — all without any cloud dependency.

Why it exists. Many small and mid-size plants still track presence with paper sign-in sheets or shared spreadsheets — error-prone, easy to manipulate, and disconnected from shift planning. The goal of this project was a single, self-hosted application that treats the barcode badge scan as the source of truth, applies the plant's real working-time rules automatically, and keeps a fully auditable record of every scan attempt — accepted or not.

One scanner thread is started per enabled scanner with automatic reconnects. Every scan flows through a single AttendanceEngine.process() decision point, so validation is identical whether it arrives from a real serial scanner, the bundled simulator, or a manual test. Rejected events are never dropped — they are stored as scan events and as exception records for review.

Capabilities

What the system actually does

📟

Touch kiosk mode

Full-screen, employee-facing screen with a large live clock, readiness status and a clear ✓ / ⚠ result after every scan. No records or settings are exposed; the only action is an administrator login.

🏷

Code 128 badge barcodes

Employees are created with sequential IDs (EMP000001, EMP000002…) and each gets a barcode image containing only their ID — plus bulk import from an Excel/CSV template with a built-in template generator.

🕒

Real shift rules engine

Regular and overnight shifts, early-arrival windows, earliest-permitted clock-out, duplicate-scan blocking, and IN/OUT decided from the employee's open session — ported faithfully into the interactive demo.

🔁

Weekly rotating shifts

Ordered rotation cycles (e.g. Schimb 1 → 2 → 3) that advance every Monday, with staggered start shifts per member. Current-week shift drives validation; past sessions keep the shift recorded at clock-in.

📊

Admin dashboard & reports

Eight live KPI cards (present now, missing clock-out, exceptions, scans…), filterable attendance with totals by shift, a full scan-event log and an exceptions view — Excel export with optional scheduled jobs.

📡

Terminals & scanners

Configure terminals and per-port scanners (COM port, baud), test a port, or test a scan input end-to-end. The repo even ships a Honeywell scanner simulator for full offline testing.

🕓

Offline-first + optional sync

A durable offline queue preserves events the primary store could not accept, and optional LAN/server synchronization lets several kiosks share a central database.

🔒

Security & audit

PBKDF2-SHA256 password hashing with a random salt (no plain text), role separation between kiosk and administrator, timestamped database backups and a full audit log of administrator actions.

Domain logic

Scan validation rules

Each badge scan is classified and, if rejected, the reason is stored. The same decision logic drives the interactive demo.

OutcomeMeaningRecorded as
CLOCK INValid IN for the employee's current shift (early arrival window respected, late arrivals allowed)Session opened
CLOCK OUTValid OUT closes the open session (earliest clock-out respected)Session closed
UNKNOWN_BARCODEBadge matches no employeeException
INACTIVE_EMPLOYEEEmployee exists but is deactivatedException
INVALID_SHIFTNo active shift applies to the employeeException
DUPLICATE_SCANSecond scan by the same employee inside the duplicate window (default 5 s)Exception
CLOCK_IN_TOO_EARLYBefore start − early-arrival minutes (e.g. 06:00 shift, 60 min → earliest 05:00)Exception
CLOCK_OUT_NOT_ALLOWEDBefore end − earliest-clock-out minutes (e.g. 14:00 shift, 10 min → earliest 13:50)Exception
💡 Overnight shifts work automatically: an end time ≤ start time (e.g. 22:00 → 06:00) is treated as crossing midnight, and scans near the pre-start window are validated against the previous day's shift.
Weekly rotation

Rotating shifts — every Monday

A rotation is an ordered cycle of shifts. Members move one step along the cycle each Monday; members can start staggered on different shifts. Example cycle Schimb 1 → Schimb 2 → Schimb 3 with members A, B, C starting on shifts 1, 2 and 3:

WeekMember AMember BMember C
1Schimb 1 (06–14)Schimb 2 (14–22)Schimb 3 (22–06)
2Schimb 3 (22–06)Schimb 1 (06–14)Schimb 2 (14–22)
3Schimb 2 (14–22)Schimb 3 (22–06)Schimb 1 (06–14)
4…cycle repeats

Why it matters

  • Fairly distributes morning, evening and night work
  • Validation always uses the shift that applies to the current week
  • Past sessions keep the shift recorded when the employee actually clocked in
  • No manual shift reassignment each week

Data model (SQLite)

  • employees · shifts · shift_rotations
  • attendance_sessions (clock-in / clock-out)
  • scan_events — every attempt retained
  • exceptions · terminals · scanners
  • export_jobs · audit_log

An automated test suite verifies the domain rules against isolated temporary databases — employee creation, early IN, too-early OUT, valid OUT, duplicate scans, unknown / inactive barcodes, overnight shifts, scanner identity, authentication and backups. The application is packaged to a Windows executable with a signed distribution build and a bilingual (EN/RO) user guide included alongside it.
